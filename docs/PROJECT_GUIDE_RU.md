# СкладAI — полный гайд по проекту (для тех, кто будет чинить)

Этот документ объясняет проект **очень простыми словами**. Если ты впервые открыл
код и ничего не понимаешь — читай отсюда. Цель: чтобы ты мог найти нужный файл,
понять «зачем он» и спокойно что-то поправить, ничего не сломав.

> Коротко: **СкладAI** — это сайт для управления складом строительных
> инструментов. Загружаешь Excel с товарами → видишь дашборд, риски, план
> закупок, заказы поставщикам, ABC/XYZ-анализ, уведомления и можешь спросить
> встроенного AI-советника.

## 1. Из чего вообще состоит проект (общая картина)

Представь ресторан:

- **Frontend (фронт)** — это «зал и официант». То, что видит пользователь в
  браузере: кнопки, таблицы, экраны. Лежит в папке `frontend/`. Написан на
  **чистом JavaScript** (без React/Vue) — просто набор `.js`-файлов.
- **Backend (бэк)** — это «кухня». Принимает запросы от фронта, считает, лезет в
  базу, отдаёт ответ. Лежит в `backend/`. Написан на **Python** с фреймворком
  **FastAPI**.
- **База данных (БД)** — это «склад продуктов кухни». Хранит все товары,
  пользователей, заказы. Для локальной разработки это файл **SQLite**
  (`backend/data/dev.db`), для «боевого» сервера — **PostgreSQL**.
- **AI-советник** — отдельный «консультант». Это локальная нейросеть (модель
  **qwen3** через программу **Ollama**), к которой бэк обращается через агент
  **Claw**. Подробно — в разделе 9.

Как они общаются: фронт шлёт бэку запросы по HTTP на адреса вида `/api/...`
(например `/api/products`). Бэк отвечает данными в формате **JSON** (текст в
фигурных скобках). Фронт берёт JSON и рисует таблицы/экраны.

```
Браузер (frontend/*.js)  →  HTTP /api/...  →  FastAPI (backend/app/*)  →  База (SQLite/Postgres)
        ↑                                                                      │
        └──────────────────────  JSON-ответ  ←─────────────────────────────────┘
```

## 3. Карта папок (где что лежит)

```
StoreAI/
├─ backend/                  ← «кухня» (Python)
│  ├─ app/
│  │  ├─ main.py             ← точка входа: собирает всё приложение
│  │  ├─ config.py           ← настройки (читает .env)
│  │  ├─ database.py         ← подключение к базе
│  │  ├─ models.py           ← описание таблиц базы
│  │  ├─ schemas.py          ← формы данных для входа/выхода (валидация)
│  │  ├─ security.py         ← пароли, токены, проверка прав
│  │  ├─ routers/            ← «адреса» /api/... (по одному файлу на тему)
│  │  └─ services/           ← бизнес-логика (где реально считается)
│  ├─ migrations/            ← история изменений структуры базы (Alembic)
│  ├─ scripts/               ← вспомогательные скрипты (демо-данные)
│  ├─ tests/test_api.py      ← автотесты
│  ├─ requirements.txt       ← список Python-библиотек
│  └─ alembic.ini            ← настройка миграций
├─ frontend/                 ← «зал» (то, что видно в браузере)
│  ├─ index.html             ← главная страница, подключает все .js
│  ├─ styles.css             ← всё оформление (цвета, отступы)
│  └─ js/                    ← логика интерфейса (по файлу на экран)
├─ .env                      ← локальные настройки (НЕ в git, секреты)
├─ .env.example              ← пример настроек (в git, без секретов)
├─ README.md                 ← краткая инструкция
└─ docs/                     ← документация (этот файл)
```

**Главное правило навигации:**
- Нужно поменять **что показывается** → ищи в `frontend/js/`.
- Нужно поменять **что считается/хранится** → ищи в `backend/app/services/` или `models.py`.
- Нужно поменять **адрес/права доступа** → ищи в `backend/app/routers/`.

## 4. Backend пофайлово (самое важное)

### `backend/app/main.py` — сборщик приложения
**Зачем:** это «главный рубильник». Создаёт приложение FastAPI, при старте
готовит базу, подключает все группы адресов (роутеры) и отдаёт фронтенд.
**Что внутри простыми словами:**
- при запуске вызывает `init_db()` — создаёт таблицы и админа (см. `database.py`);
- настраивает CORS (разрешает браузеру обращаться к API);
- строкой `app.include_router(...)` подключает каждый файл из `routers/`;
- отдаёт файлы из `frontend/` и саму страницу `index.html`.
**Когда сюда лезть:** если добавил **новый файл-роутер** в `routers/` — его надо
здесь подключить (`from .routers import ... ` + `app.include_router(...)`), иначе
новые адреса работать не будут.

### `backend/app/config.py` — настройки
**Зачем:** все «крутилки» проекта в одном месте. Читает переменные окружения и
файл `.env`.
**Что настраивает:** адрес базы (`DATABASE_URL`), секретный ключ для токенов
(`SECRET_KEY`), логин/пароль админа по умолчанию, и всё про AI: путь к Claw,
модель (`CLAW_MODEL`), таймаут, `OLLAMA_HOST`, `CLAW_NO_THINK` и т.д.
**Когда сюда лезть:** хочешь добавить новую настройку (например лимит чего-то) —
добавь поле в класс `Settings` через `os.getenv(...)`.

### `backend/app/database.py` — подключение к базе
**Зачем:** соединяет приложение с базой данных.
**Что внутри:**
- `engine`, `SessionLocal` — «соединение» и «сессии» к базе;
- `Base` — родитель всех таблиц (модели наследуются от него);
- `get_db()` — выдаёт сессию каждому запросу и закрывает после;
- `run_migrations()` — прогоняет миграции (приводит структуру базы к актуальной);
- `init_db()` — при старте делает миграции + создаёт админа.
**Когда сюда лезть:** почти никогда. Структуру базы меняют через `models.py` +
миграции, а не тут.

### `backend/app/models.py` — таблицы базы (ОЧЕНЬ ВАЖНЫЙ)
**Зачем:** описывает, **какие таблицы есть и какие у них колонки**. Каждый класс
= одна таблица.
**Что за таблицы:**
- `User` — пользователи (логин, роль admin/manager/buyer, активен ли).
- `Product` — товары (артикул, остаток, цены, поставщик, флаги риска и т.д.). Это
  центральная таблица.
- `Supplier` — поставщики (контакты, надёжность, срок).
- `ImportBatch` + `ProductSnapshot` — история загрузок Excel (для сравнения
  периодов и ABC/XYZ).
- `StockMovement` — движения склада (приход/списание/продажа…).
- `AuditLog` — журнал «кто что сделал».
- `Notification` — уведомления (заканчивается товар и т.п.).
- `PurchaseOrder` + `PurchaseOrderItem` — заказы поставщикам и их позиции.
- Ещё тут `enum`-ы (списки значений: роли, типы движений, статусы заказа) и
  `ORDER_TRANSITIONS` (какие переходы статусов заказа разрешены).
**Когда сюда лезть:** хочешь **добавить новое поле товару** (например «вес») —
добавляешь колонку в класс `Product`. НО: после этого **обязательно нужна
миграция** (см. раздел 6), иначе в базе колонки не будет и всё упадёт.

### `backend/app/schemas.py` — формы данных (валидация)
**Зачем:** описывает, **как должны выглядеть данные на входе и выходе** API.
Это «пропускной контроль»: если фронт прислал мусор — Pydantic его отклонит.
**Разница с `models.py`:** models = как лежит в базе; schemas = как приходит/уходит
по API. Это разные вещи (часто похожие, но не одно и то же).
**Когда сюда лезть:** добавил поле в модель и хочешь, чтобы его можно было
задавать/получать через API — добавь его в соответствующую схему (`ProductCreate`,
`ProductUpdate`, `ProductOut` и т.п.).

### `backend/app/security.py` — пароли, токены, права
**Зачем:** всё про «кто ты и что тебе можно».
**Что внутри:**
- `hash_password` / `verify_password` — хранение паролей в зашифрованном виде
  (PBKDF2, не открытым текстом).
- `create_access_token` / `decode_access_token` — выдаёт и проверяет токен
  (это «пропуск», который фронт носит в каждом запросе).
- `get_current_user` — по токену находит пользователя; если токен плохой или юзер
  отключён — ошибка 401.
- `require_roles(...)` — «пускать только этих ролей» (например только админа).
**Когда сюда лезть:** менять механизм входа/прав. В обычных задачах — не трогать.

### `backend/app/routers/` — адреса API
Каждый файл = группа адресов по теме. Внутри функции с декораторами вроде
`@router.get("")` или `@router.post("/upload")`. Это «двери», в которые стучится
фронт. Роутер обычно: проверяет права → зовёт нужный сервис → отдаёт результат.

- `auth.py` — вход (`/api/auth/login`), «кто я» (`/me`), смена своего пароля.
- `users.py` — пользователи: список, создать, изменить роль/активность, сбросить
  пароль (только админ).
- `products.py` — товары: список, карточка, создать/изменить/удалить, ручная
  правка риска, движения склада.
- `suppliers.py` — поставщики (CRUD).
- `orders.py` — заказы поставщикам: создать из плана, сменить статус, удалить.
- `procurement.py` — план закупок (что и сколько заказать).
- `imports.py` — загрузка Excel: предпросмотр и сам импорт, скачать шаблон.
- `analytics.py` — дашборд и ABC/XYZ.
- `reports.py` — PDF-отчёт по рискам.
- `notifications.py` — уведомления: список, пересканировать, отметить прочитанным.
- `audit.py` — журнал действий (только админ).
- `ai_chat.py` — AI-чат: обычный ответ (`/chat`) и потоковый (`/chat/stream`),
  статус AI (`/status`).
**Когда сюда лезть:** хочешь **новый адрес API** — добавь функцию в подходящий
роутер. Хочешь **новую тему** — создай новый файл-роутер и подключи его в `main.py`.

### `backend/app/services/` — бизнес-логика (где реально думают)
Роутеры тонкие — вся «умная» логика тут. Если надо поменять **как что-то
считается**, тебе сюда.

- `analytics.py` — **сердце аналитики.** `product_signal(product)` решает статус
  риска товара («Срочно заказать», «Мертвый груз» и т.п.) и считает дни до
  нуля, маржу. `build_dashboard()` собирает данные для дашборда. Если хочешь
  поменять **правила риска** — это здесь.
- `procurement.py` — считает план закупок: что заказать и сколько
  (`recommended_order_qty`).
- `abc_xyz.py` — ABC/XYZ-классификация (ABC = вклад в выручку, XYZ = стабильность
  спроса).
- `excel_import.py` — разбор Excel-файла: распознаёт колонки, чистит числа/даты,
  создаёт/обновляет товары, делает снимок (snapshot), авто-привязывает поставщика.
- `movements.py` — применяет движение склада (меняет остаток, не даёт уйти в минус).
- `orders.py` — собирает заказы из плана (группирует по поставщикам), меняет
  статусы; при «получен» делает приход на склад.
- `notifications.py` — правила уведомлений (заканчивается / залежался / низкая
  маржа) + событие после импорта.
- `audit.py` — `record_audit(...)` пишет строку в журнал «кто что сделал».
- `pdf_report.py` — генерация PDF-отчёта.
- `initial_data.py` — создаёт админа при первом запуске.
- `ai_service.py` — **мозг AI-чата** (самый большой файл, ~1200 строк). Решает,
  ответить ли локально-быстро (без модели) или сходить к нейросети; чистит ответ
  модели; делает потоковый ответ. Подробно — раздел 9.
- `claw_agent.py` — запускает программу Claw (нейросеть) и забирает её ответ;
  проверяет, готов ли AI (есть ли бинарь и провайдер).

### `backend/migrations/` — изменения структуры базы (Alembic)
**Зачем:** когда меняешь `models.py`, базе нужно «узнать» об этом. Миграции — это
пронумерованные файлы-инструкции «добавь такую-то колонку/таблицу».
- `versions/0001_initial_schema.py` — вся стартовая схема.
- `0002_notifications.py`, `0003_purchase_orders.py` — последующие изменения.
- `env.py` — настройка, берёт адрес базы из `config.py`.
**Когда сюда лезть:** см. раздел 6 (это обязательный шаг при изменении моделей).

### `backend/tests/test_api.py` — автотесты
**Зачем:** проверяют, что API работает. Гоняй после каждой правки. Если добавил
функциональность — добавь сюда тест по образцу соседних.

### Прочее
- `requirements.txt` — список библиотек (`pip install -r`).
- `scripts/seed_demo_data.py` — заполняет базу демо-товарами для проверки.
- `alembic.ini` — конфиг миграций.

## 5. Frontend пофайлово

Фронт — это **обычные `.js`-файлы, которые грузятся по порядку** (см. `index.html`)
и делят общие переменные (`state`, функция `render`, помощники). Тут **нет сборки**
(webpack/vite) — что написал, то и работает.

### Как фронт устроен (важно понять один раз)
- Есть один объект **`state`** — это «вся память интерфейса» (кто залогинен,
  какой экран открыт, какие товары загружены и т.д.).
- Есть функция **`render()`** — она по `state` целиком перерисовывает страницу
  (берёт HTML-шаблон нужного экрана и вставляет в `<div id="root">`).
- Любое действие меняет `state` и зовёт `render()`. Всё.

### `frontend/index.html` — каркас
**Зачем:** пустая страница с `<div id="root">` и списком `<script>`, которые
грузят все `.js` **по порядку** (`core.js` первый, `boot.js` последний).
**Важный момент — кэш:** у скриптов есть `?v=local-6`. Браузер кэширует файлы по
этому адресу. **Если поменял `.js`, но в браузере старое — увеличь число**
(`local-6` → `local-7` во всех строках), это заставит браузер скачать свежее.

### `frontend/js/core.js` — ядро (самый главный JS)
**Зачем:** тут живут `state`, `render()`, помощники (`api()` для запросов к бэку,
`escapeHtml`, `formatMoney`, `csvCell` и др.), боковое меню, маршрутизация
(какой экран показать), и экран **Дашборд**.
**Ключевые места:**
- `NAV_ITEMS` — пункты меню. Добавляешь экран → добавляешь сюда пункт.
- `state = {...}` — добавляешь экран → добавляешь сюда «ячейку» для его данных.
- `activeTemplate()` / `bindActiveScreen()` / обработчик меню — здесь связывается
  «id экрана» → «функция-шаблон» и «функция-привязка кнопок».
- `api(path, options)` — обёртка над `fetch`: сама подставляет токен и обрабатывает
  ошибки. Используй её для всех запросов (кроме потокового чата).

### `frontend/js/boot.js` — запуск
**Зачем:** одна строка `render();` в самом конце. Грузится последним, чтобы все
функции уже были определены. Не трогать.

### Экранные файлы (каждый = один раздел сайта)
Шаблон у всех одинаковый: функция `xxxTemplate()` возвращает HTML, `bindXxx()`
вешает обработчики на кнопки, `loadXxx()` тянет данные с бэка.
- `warehouse.js` — экран **Склад** + карточка товара (модалка) + движения.
- `procurement.js` — **Закупки** (план + кнопка «Сформировать заказ» + CSV).
- `orders.js` — **Заказы** поставщикам (статусы, позиции, CSV).
- `risks.js` — **Риски** (фильтры, быстрые действия, ручная правка риска).
- `abc.js` — **ABC/XYZ** (матрица + таблица; ещё вставка на дашборд).
- `notifications.js` — **Уведомления** (всплывашка-колокольчик).
- `chat.js` — **AI-советник** (чат, потоковый вывод токенов).
- `imports.js` — **Excel** (загрузка, предпросмотр, история).
- `screens.js` — остальные экраны: **Отчёты, Пользователи, Аудит, Поставщики,
  Настройки** (включая смену своего пароля).

### `frontend/styles.css` — всё оформление
**Зачем:** цвета, отступы, размеры. Цветовая палитра задана сверху в `:root`
(переменные `--bg`, `--yellow` и т.д.). Хочешь сменить тему — меняй эти переменные.

## 6. КАК ДОБАВИТЬ ПОЛЕ ТОВАРУ (полный пример — самая частая задача)

Допустим, надо добавить товару поле «вес» (`weight`). Шаги **по порядку**:

1. **Модель** — в `backend/app/models.py`, класс `Product`, добавь колонку:
   ```python
   weight: Mapped[float] = mapped_column(Float, default=0)
   ```
2. **Миграция** — создай файл-инструкцию для базы:
   ```powershell
   .\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini revision --autogenerate -m "product weight"
   .\.venv\Scripts\python.exe -m alembic -c backend\alembic.ini upgrade head
   ```
   (autogenerate сам увидит новую колонку и напишет миграцию; upgrade применит её
   к базе.) **Без этого шага колонки в базе не будет и будут ошибки.**
3. **Схемы** — в `backend/app/schemas.py` добавь `weight` в `ProductCreate` и
   `ProductUpdate` (чтобы можно было задавать через API).
4. **Отдача наружу** — в `backend/app/services/analytics.py`, функция
   `product_to_dict`, добавь `"weight": product.weight` (чтобы фронт его видел).
5. **Фронт** — в `frontend/js/warehouse.js` в форме карточки товара добавь поле
   ввода `weight` и включи его в чтение формы.
6. Прогони `pytest`, перезапусти сайт, увеличь `?v=local-N` в `index.html`.

> Если пропустишь шаг 2 (миграцию) — приложение упадёт с ошибкой «нет такой
> колонки». Это самая частая ошибка новичка.

## 8. Роли и права (кому что можно)

- **admin** — может всё (пользователи, удаление, аудит, настройки).
- **manager** — товары, риски, импорт, заказы, поставщики, отчёты.

просто прячутся для ролей без прав, но **настоящая защита — на бэке**.

## 9. Как работает AI-советник (самое мудрёное)

Идея: пользователь пишет вопрос в чат → бэк решает, как ответить. Есть три уровня:

1. **Быстрый локальный ответ (без нейросети).** Файл `ai_service.py`, функция
   `_fast_local_chat`. Если вопрос типовой («что заказать», «риски», «бюджет
   100000», «привет») — отвечаем сразу своими формулами по данным склада.
   Это **мгновенно** и надёжно.
2. **Нейросеть (qwen3 через Ollama).** Если вопрос «свободный»/аналитический —
   идём к модели. Тут два пути:
   - обычный (`/api/ai/chat`) — ждём весь ответ через программу **Claw**;
   - потоковый (`/api/ai/chat/stream`) — печатаем ответ по словам, обращаясь
     **напрямую к Ollama** (потому что Claw отдаёт ответ только целиком и
     «печатать» не умеет).
3. **Запасной вариант.** Если нейросеть недоступна — снова отвечаем локальными
   правилами. Сайт работает всегда, даже без модели.

**Важные настройки AI (в `.env`):**
- `CLAW_MODEL=qwen3:latest` — какая модель.
- `OLLAMA_HOST=http://127.0.0.1:11434` — где крутится Ollama.
- `CLAW_NO_THINK=true` — отключает «размышления» модели. Это критично: без него
  qwen3 (а) лезет читать файлы и отвечает «файл не найден», (б) думает ~68 секунд.
  С ним — не лезет и думает вдвое быстрее.

**Если AI «тупит» или молчит:**
- Проверь, что Ollama запущена: открой `http://127.0.0.1:11434` — должно
  отвечать. Или `ollama list` в терминале.
- Проверь статус: открой в браузере (залогинившись) `/api/ai/status`.
- Первый ответ модели всё равно идёт ~15-20 сек (это «прогрев» на большом
  контексте) — это нормально, не баг.

## 10. Грабли и правила (чтобы не сломать)

1. **После правки `models.py` — всегда миграция** (раздел 6). Иначе «нет колонки».
2. **После правки `.js` — увеличь `?v=local-N`** в `index.html`, иначе браузер
   покажет старую версию из кэша (легко потерять час, думая «почему не работает»).
3. **После любой правки — `pytest`.** Зелёные тесты = ничего не сломал.
4. **`.env` не коммить** — там локальные настройки. В git только `.env.example`.
5. **Предупреждения git про «LF will be replaced by CRLF»** — это нормально
   (Windows-перевод строк), не ошибка, можно игнорировать.
6. **Новый роутер не работает?** — забыл подключить его в `main.py`.
7. **Не правь файлы в `migrations/versions/`, которые уже применены** — создавай
   новую миграцию. Старые менять нельзя.
8. **Демо-БД `backend/data/dev.db`** — это просто локальный файл. Если он «битый»
   или со старой структурой — можно удалить, при следующем запуске создастся
   заново из миграций (и появится только админ). Демо-**товары** автоматически не
   добавляются — для них есть отдельный ручной скрипт:
   `.\.venv\Scripts\python.exe backend\scripts\seed_demo_data.py`.

## 11. Путь одного запроса (для понимания, как всё связано)

Пример: пользователь нажал «Найти» на экране Склад.

1. `frontend/js/warehouse.js` → функция `loadProducts()` вызывает
   `api("/api/products?search=дрель")`.
2. `api()` (в `core.js`) шлёт HTTP-запрос с токеном.
3. Бэк: `routers/products.py` ловит `/api/products`, проверяет права
   (`get_current_user`), берёт товары из базы (`models.py` → `Product`).
4. Для каждого товара зовётся `services/analytics.py` → `product_to_dict` (считает
   статус риска и т.п.).
5. Список JSON летит обратно.
6. `loadProducts()` кладёт его в `state.warehouse.rows` и зовёт `render()`.
7. `render()` рисует таблицу из шаблона `warehouseTemplate()`.

Понял эту цепочку — понял весь проект. Все остальные экраны устроены так же.
